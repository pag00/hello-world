# StepTrack — Architecture & Contract

Procedure authoring and execution for manual assembly, built to satisfy
AS9100 / EN 9100 record-keeping (revision control, traceability, immutable
as-run records, nonconformance handling).

This document is the **contract** between the server, the core library and
the apps. If code and this document disagree, fix one of them deliberately.

## 1. Repository layout

```
packages/core/     @steptrack/core   Vue 3 library: domain, offline DB, sync,
                                    auth, device adapters, components, routes
apps/web/          @steptrack/web    Standalone shell (PWA + Capacitor Android)
server/            steptrack-server  FastAPI + SQLAlchemy + Alembic, Postgres, S3
spec/test-vectors/                  Shared fixtures both TS and Python must pass
docs/                               This file, ops notes
```

The workspace webapp integrates by installing `@steptrack/core` and calling
`installStepTrack(app, { router, basePath, auth, apiBaseUrl })` (see §9).

## 2. Roles

| Role         | May                                                               |
|--------------|-------------------------------------------------------------------|
| `operator`   | execute steps, record values/photos/scans, raise NCR              |
| `inspector`  | everything operator may + countersign verification steps          |
| `author`     | create/edit draft procedure revisions, submit for review          |
| `approver`   | approve/reject revisions in review (never their own revision)     |
| `supervisor` | NCR disposition, resolve conflicts, abort/close runs, take over locks |
| `admin`      | users, tools/calibration, workstations                            |

A user may hold several roles. Role checks happen on the server; the client
only hides UI.

## 3. Domain model

All ids are **UUIDv7** strings generated by whoever creates the object
(clients generate ids for runs, events, NCRs, blobs-by-hash), so offline
creation needs no server round-trip and ingest is idempotent.

### 3.1 Procedure & revisions

```
Procedure        { id, number ("ASM-0042"), title, created_at }
ProcedureRevision{ id, procedure_id, rev ("A","B",...), status, content,
                   content_hash, change_reason, author_id, created_at,
                   submitted_at, released_at, obsoleted_at }
Approval         { id, revision_id, approver_id, decision: approve|reject,
                   comment, signed_at }
```

Revision status machine (server-enforced):

```
draft --submit--> in_review --approve--> released --(next rev released)--> obsolete
                      \--reject--> draft
```

- Only `draft` content is mutable. `content_hash` is recomputed on submit and
  frozen from then on.
- Approval requires a user with `approver` role who is **not** the author.
- Releasing rev N+1 marks the previously released revision `obsolete`.
  Running runs keep their pinned revision.
- `change_reason` is required for every revision after the first.

### 3.2 Revision content (JSON, stored as `content`)

```jsonc
{
  "schema": 1,
  "sections": [
    {
      "id": "uuid", "title": "Prepare bulkhead",
      "steps": [
        {
          "id": "uuid",                 // stable across revisions when "same" step
          "title": "Torque M6 bolts",
          "instructions": "markdown",
          "media": ["sha256:..."],      // reference images (blobs)
          "locations": ["WS-03"],       // workstation codes; QR at WS-03 jumps here
          "depends_on": ["stepId"],     // must be completed first; empty = free
          "verification": { "required": true, "role": "inspector" }, // optional
          "inputs": [ /* Input, see below */ ]
        }
      ]
    }
  ]
}
```

`Input` variants (discriminated by `type`), all have `id` (uuid), `label`,
`required` (bool):

| type      | extra fields                                                          | value recorded                         |
|-----------|-----------------------------------------------------------------------|----------------------------------------|
| `check`   | —                                                                     | `true`                                 |
| `text`    | `multiline?`                                                          | string                                 |
| `number`  | `unit`, `min?`, `nominal?`, `max?`, `decimals`, `ocr` (bool)          | **decimal string**, e.g. `"12.50"`     |
| `photo`   | `min_count` (≥1 if required), `max_count?`                            | list of `sha256:<hex>` blob refs       |
| `scan`    | `entity`: `part` \| `tool` \| `any`, `expect?` (regex or exact value) | scanned identifier string              |
| `signoff` | `role?` (role required to sign)                                       | `true` (who/when lives on the event)   |

Number limits are decimal strings too (`"min": "11.5"`). **No floats anywhere
in hashed content** (see §5).

A `number` outside `[min,max]` → the step result is recorded as
`out_of_tolerance` and the step cannot be completed until an NCR exists for it.

A `scan` with `entity: tool` triggers a calibration check against the tool
registry: expired or unknown tool → blocked (online) / flagged (offline,
re-checked on ingest, flagged event + NCR required if expired).

### 3.3 Runs

```
Run { id, procedure_id, revision_id, serial (unit/assembly serial),
      work_order?, status: active|blocked|completed|aborted,
      created_by, created_at, closed_at }
```

The run's **state is a projection of its event ledger** (§4). `status` is a
server-maintained cache of that projection.

### 3.4 Supporting entities

```
Tool        { id, code ("TW-017"), description, calibration_due (date), active }
Workstation { code ("WS-03"), name }
NCR         { id, run_id, step_id?, input_id?, number ("NCR-2026-0012"),
              description, status: open|dispositioned|closed,
              disposition?: use_as_is|rework|repair|scrap|return_to_supplier,
              disposition_note?, raised_by, raised_at, dispositioned_by?, ... }
Blob        { sha256, size, mime, created_at }   // bytes in S3 at key blobs/<sha256>
User        { id, oidc_sub, name, email, roles[] , pin_verifier? }
```

NCR lifecycle changes are **also** recorded as run events (`ncr.raised`,
`ncr.dispositioned`, `ncr.closed`) so the run record is self-contained.

## 4. Run event ledger (append-only)

Every fact about a run is an immutable event. Nothing is updated or deleted;
corrections are new events that reference the corrected one.

```jsonc
RunEvent {
  "id": "uuidv7",
  "run_id": "uuid",
  "type": "<see table>",
  "step_id": "uuid|null",
  "payload": { ... },              // type-specific, no floats
  "actor_id": "user uuid",
  "auth_method": "oidc" | "pin",
  "device_id": "uuid",             // stable per installed client
  "client_ts": "2026-10-22T10:31:05.123Z",   // device clock, UTC, ms, 'Z'
  "offline": true|false,           // created while offline
  "supersedes": "event id|null",   // correction of an earlier event
  "content_hash": "sha256:<hex>",  // client-computed, §5
  // server-assigned on ingest:
  "seq": 17, "prev_chain_hash": "sha256:...", "chain_hash": "sha256:...",
  "server_ts": "...", "flags": ["conflict" | "unlocked" | "late_lock" | "tool_expired" | ...]
}
```

| type                 | step_id | payload                                                       |
|----------------------|---------|---------------------------------------------------------------|
| `run.created`        | null    | `{procedure_id, revision_id, serial, work_order}`             |
| `step.started`       | yes     | `{}`                                                          |
| `input.recorded`     | yes     | `{input_id, value, source: "manual"\|"ocr"\|"scan", ocr_raw?}`|
| `step.completed`     | yes     | `{}` (server re-validates all required inputs present & ok)   |
| `step.verified`      | yes     | `{}` (actor must hold verification role, ≠ completer)          |
| `step.reopened`      | yes     | `{reason}` (supervisor)                                       |
| `note.added`         | any     | `{text}`                                                      |
| `ncr.raised`         | any     | `{ncr_id, number?, description, input_id?}`                   |
| `ncr.dispositioned`  | any     | `{ncr_id, disposition, note}` (supervisor)                    |
| `ncr.closed`         | any     | `{ncr_id}`                                                    |
| `conflict.resolved`  | yes     | `{kept_event_ids[], rejected_event_ids[], reason}` (supervisor)|
| `run.completed`      | null    | `{}` (server checks: all steps completed/verified, no open NCR or conflict) |
| `run.aborted`        | null    | `{reason}` (supervisor)                                       |

### Projection rules (client & server implement identically)

1. **Order**: events with `seq` first, ascending by `seq`; then events without
   `seq` (local, not yet accepted) by `client_ts`, then `id`.
2. **Dead events**: an event is dead if another event `supersedes` it, or a
   `conflict.resolved` lists it in `rejected_event_ids`. Dead events are
   ignored by every rule below (they stay in the ledger and the record).
3. **Inputs**: per `input_id`, the value is the last live `input.recorded`.
   A `number` value outside `[min, max]` (decimal comparison, bounds
   inclusive, missing bound = unbounded) is `out_of_tolerance`.
4. **Step flags**: a step is in **conflict** if any live event for it carries
   flag `conflict` and no later `conflict.resolved` for that step exists.
5. **Completion**: a step is completed if a live `step.completed` exists after
   the last live `step.reopened` of that step. Verified if additionally a live
   `step.verified` exists after that `step.completed`.
6. **NCR coverage**: an NCR (from `ncr.raised`) covers a step/input when its
   `step_id` matches and (`input_id` matches or the NCR has no `input_id`).
7. **Block reasons** (only evaluated for steps not completed):
   - `depends_on`: some dependency is not completed/verified
   - `out_of_tolerance`: some number input is out of tolerance and not covered by an NCR
   - `tool_expired` / `tool_unknown`: the live input event carries that flag and is not covered by an NCR
8. **Step state**, first match wins: `conflict` → `verified` → `completed` →
   `blocked` (any block reason) → `in_progress` (any live step event) → `pending`.
9. **NCR status**: `open` after `ncr.raised`, `dispositioned` after
   `ncr.dispositioned`, `closed` after `ncr.closed`. `open_ncr_ids` = not closed.
10. **Run status**: `aborted` if live `run.aborted`; else `completed` if live
    `run.completed`; else `blocked` if any step is `conflict` or blocked for a
    reason other than `depends_on`; else `active`.
11. **can_complete**: status `active`, every step `completed` or `verified`,
    every step with `verification.required` is `verified`, no open NCR.

**Validation on write** (client before creating, server on ingest → 422):
`step.completed` requires all `required` inputs to have a value (photo:
≥ `min_count` refs) and no non-`depends_on` block reason; `step.verified`
requires the step completed, actor holds `verification.role` and is not the
completer; `scan` value must match `expect`; `signoff.role` must be held by
the actor; `run.completed` requires `can_complete` and role `inspector` or
`supervisor`; supervisor-only types (`step.reopened`, `ncr.dispositioned`,
`ncr.closed`, `conflict.resolved`, `run.aborted`) require `supervisor`;
everything else requires `operator` (inspectors and supervisors may also
operate). Events on a `completed`/`aborted` run are rejected.

Shared fixtures in `spec/test-vectors/projection/*.json` define
`{revision_content, events[], expected_step_states}`; both implementations
must pass them.

## 5. Canonical hashing

`content_hash = "sha256:" + hex(sha256(utf8(canonical_json(E))))` where `E`
is the event **without** `content_hash` and without any server-assigned field
(`seq, prev_chain_hash, chain_hash, server_ts, flags`).

`canonical_json`:
- objects: keys sorted by Unicode code point, recursively
- no insignificant whitespace (`,` and `:` separators)
- strings: JSON-escaped with **only** the mandatory escapes (`"` `\\` and
  control chars < 0x20 as `\uXXXX` except `\b \f \n \r \t`); non-ASCII emitted
  as raw UTF-8
- numbers: **integers only**, |n| ≤ 2^53−1; floats are a validation error
- `true`/`false`/`null` literal

Python: `json.dumps(obj, sort_keys=True, separators=(",",":"), ensure_ascii=False)`
matches this given the no-float rule. TS: implemented in
`packages/core/src/domain/canonical.ts`. Vectors: `spec/test-vectors/canonical.json`.

**Chain:** on ingest the server appends to the per-run ledger:
`chain_hash = "sha256:" + hex(sha256(utf8(prev_chain_hash + content_hash)))`,
with `prev_chain_hash` of the first event = `"sha256:" + "0"*64`.
`GET /runs/{id}/verify` recomputes all content hashes and the chain.
Revision `content_hash` = same canonical hash over `content`.

## 6. Locks, checkout and concurrency

**Hard locks, online only.** Parallel work on one run requires connectivity.

- **Step lock**: `POST /runs/{run}/steps/{step}/lock` → lease
  `{lock_id, holder_user, holder_device, expires_at}` (TTL 120 s), renewed by
  `POST /locks/{lock_id}/heartbeat` every 30 s, released by `DELETE /locks/{id}`.
  Lock is refused (409) while another unexpired lease exists; a supervisor
  may `force` take-over (logged as event `note.added` with payload
  `{text, system: "lock_takeover"}`).
- **Run checkout** (offline mode): `POST /runs/{run}/checkout` grants one
  device an exclusive lease on the whole run (TTL default 12 h, max 72 h).
  Refused if any other step lock or checkout is active. While checked out,
  no other device can lock steps of that run. Released by
  `DELETE /runs/{run}/checkout` after the device has pushed its events.
- Client may write step events offline **only** for runs it has checked
  out; otherwise the run is read-only offline (UI enforces).
- **Runs created offline** (`run.created` with `offline: true`) are implicitly
  checked out by the creating device: the client records a local checkout
  immediately, and on ingest of that `run.created` the server grants the same
  device a run checkout (default TTL) starting at the event's `client_ts`.
  Runs created online get no implicit checkout; devices use step locks.
- **Evidence is never rejected for lock reasons.** On ingest the server
  checks whether the event's `device_id` held a valid step lock or run
  checkout at `client_ts`:
  - held → accepted, no flag
  - lease expired and nobody else locked meanwhile → accepted, flag `late_lock`
  - someone else held it / results diverge → accepted, flags `conflict`
    (and `unlocked` if never held). Step enters `conflict` state until a
    supervisor posts `conflict.resolved`.
- Events are rejected (422) only for structural reasons: schema invalid,
  hash mismatch, unknown run, float in payload, actor lacks role.

## 7. Sync protocol

Client keeps an outbox (IndexedDB) of events and blobs.

```
POST /sync/push        { device_id, events: RunEvent[] }   (≤ 500 per call)
  → { results: [{id, status: "accepted"|"duplicate"|"rejected", seq?, flags?, error?}] }
     events with same id & same content_hash → "duplicate" (idempotent)
     same id, different hash → "rejected"

PUT  /blobs/{sha256}   raw bytes, Content-Type; server verifies hash, stores in S3
HEAD /blobs/{sha256}   200 if present (client skips upload)
GET  /blobs/{sha256}   bytes (or 302 to presigned S3 URL)

GET  /sync/pull?cursor=<opaque>&limit=500
  → { cursor, has_more, procedures[], revisions[] (released+obsolete, plus
      drafts/in_review for authors), runs[], events[], tools[], workstations[],
      ncrs[], users[] (id,name,roles,pin_verifier) }
```

Order on reconnect: upload blobs referenced by outbox events → push events →
pull → release checkout if requested. Pull cursor is a server-side
monotonically increasing change counter (`change_log.id`).

Blobs referenced by an event must exist before `run.completed` is accepted;
`input.recorded` with missing blobs is accepted but flagged `blob_missing`
until uploaded.

## 8. Auth

- **Online**: OIDC Authorization Code + PKCE (`oidc-client-ts`) in the
  standalone app; when embedded, the host passes an `AuthProvider`
  (`getAccessToken()`, `getUser()`). Server validates JWT against the
  issuer's JWKS (`OIDC_ISSUER`, `OIDC_AUDIENCE`), maps `sub` → User, roles
  from a configurable claim (`OIDC_ROLES_CLAIM`, default `roles`) merged with
  DB roles.
- **Dev mode** (`AUTH_MODE=dev`): `Authorization: Dev <user-id>`; seeded users
  for every role, listed unauthenticated at `GET /auth/dev-users` (404 when not
  in dev mode). Never enabled when `ENV=production`.
- `GET /me` → current `User` (with roles); `PUT /me/pin {pin}` sets the PIN.
- **Offline PIN**: each user sets a 6+ digit PIN online. Server stores
  `pin_verifier = PBKDF2-SHA256(pin, salt, 210000)` as
  `"pbkdf2-sha256$210000$<salt_b64>$<hash_b64>"` (16-byte random salt, 32-byte
  derived key, standard base64 with padding; PIN = 6–12 ASCII digits, UTF-8)
  and ships it in pull to devices.
  Offline, the device verifies the PIN locally (WebCrypto) to attribute each
  sign-off to the person at the tablet (`auth_method: "pin"`). Multiple users
  can sign on one tablet (inspector countersign).

## 9. Client architecture (`@steptrack/core`)

```
src/domain/      types.ts, canonical.ts (hashing), projection.ts, limits.ts, qr.ts
src/db/          Dexie schema: procedures, revisions, runs, events, outbox, blobs, meta
src/api/         typed fetch client (types generated from server OpenAPI → api/schema.d.ts)
src/sync/        SyncEngine: online detection, outbox flush, pull, locks/heartbeats, checkout
src/auth/        AuthProvider interface, OidcAuthProvider, DevAuthProvider, PIN verify
src/device/      Scanner, Ocr, Camera interfaces + web impls + Capacitor impls
src/stores/      Pinia stores (session, procedures, runs, sync)
src/components/  UI components (run execution, inputs, authoring, NCR, tools)
src/views/       route-level views
src/routes.ts    createStepTrackRoutes(basePath) → RouteRecordRaw[]
src/plugin.ts    installStepTrack(app, options)
src/i18n/        en.json, de.json
```

QR payloads (also valid as plain text):
`https://<host>/<basePath>/q/ws/<code>`, `/q/run/<runId>`, `/q/part/<pn>/<serial>`,
`/q/tool/<code>`; parser also accepts `st:ws:<code>`, `st:run:<id>`,
`st:part:<pn>:<serial>`, `st:tool:<code>`.

Workstation scan → finds steps of the **active run on this device** whose
`locations` include the code, picks the first actionable one.

Host integration: Vue 3 + vue-router 4 + Pinia; the host provides router and
pinia, core registers its routes under `basePath` and uses the host's i18n
instance if given, else creates its own.

## 10. Exports

`GET /runs/{id}/record.pdf` and `.json`: as-run record with procedure number
+ revision + content hash, unit serial, every event (who/when/how authenticated,
offline flag), measured values vs limits, photos (thumbnails), scanned
parts/tools with calibration status at time of use, NCRs with dispositions,
chain verification result.
